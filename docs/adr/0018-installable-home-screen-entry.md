# 0018 — Installable home-screen entry: standard manifest, minimal SW, no onboarding

- **Status:** Accepted
- **Date:** 2026-09-16
- **Provenance:** grilling session (G4) → implemented in the installable-entry feature commit

## Background

ADR-0017 gave the client a credentialless resume path: a page opened with no URL hash and a stored session token validates against `/api/stats` and enters the main screen without the PIN handshake. The remaining gap was the entry itself — a paired phone still had to open the browser, type the server URL, and (on a fresh page) get to the main screen. A home-screen icon that opens the app window directly would make the paired-device experience one tap.

The app is served over a self-signed TLS certificate on a LAN IP (ADR-0006/0015). That constraint shapes what "installable" can mean: Chromium only enables automatic install for origins that are **secure contexts**, and a self-signed certificate that the device does not trust does not make the origin secure (Chrome for Developers, "Revisiting Chrome's installability criteria"; web.dev "What does it take to be installable?"). iOS Safari's "Add to Home Screen", by contrast, works for any HTTPS page and does not depend on a manifest or a service worker.

## Decision

Ship a standards-shaped manifest, real icon files, and a **minimal service worker (register + empty fetch handler, no caching)** — without any in-app installation onboarding.

1. **Platform scope** — iOS Safari home screen is the primary target; Android Chrome is best-effort. The manifest is written to the W3C standard regardless (it is a static file, harmless on both platforms), but the acceptance matrix only promises iOS home-screen entry plus Android manual "Add to Home Screen". Chromium's automatic install prompt is **not** promised: under a self-signed certificate the origin is not a secure context, so the prompt does not appear.
2. **Manifest** (`web/manifest.webmanifest`) — `name`, `short_name`, `start_url: "/"` (no hash, so the entry route is ADR-0017's resume path), `display: "standalone"` (consistent with the existing `apple-mobile-web-app-capable` meta), `theme_color` and `background_color` matching the app's `#0a0a0f`, icons at 192×192 and 512×512. Served by the hybrid static handler (ADR-0011) with the correct `application/manifest+json` MIME (verified in `mime_guess` 2.0.5's built-in table).
3. **Icons** — independent PNG files under `web/icons/`: `icon-180.png` (apple-touch-icon), `icon-192.png`, `icon-512.png` (manifest). The apple-touch-icon `<link>` switches from the inline base64 64px favicon to `icon-180.png`; the page favicon stays inline (it is small enough and avoids an extra file). Generated by upscaling the existing hand-drawn mic mark.
4. **Minimal service worker** (`web/sw.js`) — registers with an **empty fetch handler that never intercepts** (no caching, no offline). Registered from `app.js` on load as progressive enhancement — where `navigator.serviceWorker` is unavailable (the self-signed origin is not a secure context) it is silently skipped. `worker-src 'self'` has been in the strict CSP since the initial commit, so no header change was needed; a test pins it against regression.
5. **No onboarding** — no "add to home screen" banner or hint. iOS provides no API to detect whether the app is running installed, so a hint could not dismiss itself accurately and would be permanent noise for a LAN tool.
6. **No caching** — the service worker does not touch the network path. Every request keeps flowing through the ADR-0011 handler with ETag revalidation; a cached-asset staleness class (the exact failure ADR-0011 exists to prevent) is not reintroduced.

## Reasoning

- **The minimal SW exists for the future, not today.** Under a self-signed certificate Chromium's install prompt is unreachable, and iOS does not require a SW at all — so a SW earns nothing today. But Chromium's installability criteria are stable, SW registration is one line plus an empty handler, and if a trusted-CA story (e.g. `mkcert`-style root installation) ever makes the origin a secure context, the manifest + SW pair is already in place; Chrome's criteria no longer require the SW to have a fetch handler, but a registered SW keeps the door open and passes Lighthouse audits.
- **Standards-shaped manifest despite a non-installable Android origin**: the manifest is the single source of truth for home-screen metadata on Android and, since iOS 15.4+, is read for several fields on iOS too. Cost is one static file; future-proofing is free.
- **Standalone display matches the existing meta** and the app's shape: a single full-screen page with a black background (`viewport-fit=cover`, `theme-color #0a0a0f`, black-translucent status bar) was already built for it.
- **start_url "/" (no hash) is the whole point**: it lands on the ADR-0017 resume route, so the home-screen icon opens the paired main screen with zero PIN interaction.

## Alternatives considered

- **No service worker at all** — rejected by decision: it saves one file, but forfeits the ready-made installability hook for a future trusted-CA origin at negligible cost.
- **Full offline-caching SW** — rejected: caching reintroduces the staleness class ADR-0011 exists to prevent, and offline operation is meaningless for a live LAN microphone.
- **Inline data: URL icons in the manifest** — rejected: browser support for data: URL icon sources is inconsistent; independent files are served correctly by the existing handler with zero server changes.
- **In-app install onboarding** — rejected: iOS cannot detect the installed state, so the hint cannot dismiss itself accurately.
- **Trusted-CA rollout (mkcert-style) to unlock Chromium auto-install** — out of scope: it changes the security posture (every device must trust a CA) and the pairing story; revisit separately if Android auto-install ever becomes a requirement.

## Consequences

- `web/` gains `manifest.webmanifest`, `icons/icon-180.png`, `icons/icon-192.png`, `icons/icon-512.png`, and `sw.js`; `index.html` links the manifest, points `apple-touch-icon` at the 180 file, and `app.js` registers the SW.
- The pre-existing CSP `worker-src 'self'` is now pinned by a server test; no header change shipped.
- A phone that adds the page to its home screen opens a standalone window at `/` → no hash → ADR-0017 resume → main screen without PIN (when paired).
- **iOS storage isolation (platform behavior, verified on-device)**: a Home-Screen web app on iOS keeps its storage (localStorage, cookies, IndexedDB) fully separate from Safari — the session token does **not** carry over the first time the page is opened from the icon, so that first open requires one PIN pairing inside the standalone window (the token cannot be injected across containers without putting it in the URL — a security anti-pattern). After that one pairing the home-screen entry resumes credential-free (ADR-0017). Because the server keeps a single session-token slot (ADR-0016), mixing Safari and the home-screen entry on one device re-pairs the other side on each switch; prefer committing to one entry.
- Chromium automatic install remains unavailable on self-signed origins (documented, not a regression); manual "Add to Home Screen" still works where the browser offers it.
- The service worker never intercepts requests: ADR-0011's ETag revalidation and live disk-override editing are unchanged.
- No server-side change: the new files ride the ADR-0011 embedded/disk-override handler and its MIME table.
